# DEFENSE — Завдання 1: Домен і модель даних (ER)

**Намір і критерії (1–2 речення):**
Я змоделювала онлайн-бібліотеку, де читач бронює фізичні книги, купує їх, читає цифрові версії, зберігає колекції (їх створюють автори) та створює групи. Для мене головні три критерії: модель у 3NF (єдиний виняток, `sold_price`, бо це історичний факт), відсутність сполучних таблиць там, де зв'язок «багато до багатьох» без власних даних, і збіг назв полів та типів id у діаграмі й spec.

**Топ-3 розбіжності (spec ↔ артефакт) + коміт-виправлення:**
- Розбіжність 1. Типи полів
  - Spec (`c4c2bef`): тип задано лише для id (`number`), для решти полів типів немає.
  - Діаграма (`392deee`): усі поля мають типи (`string`, `number`, `boolean`, `date`, `datetime`), їх призначив промт, а не spec.
  - Виправлення: два коміти.
    - `spec: add field types`, тип для кожного поля в spec. SHA: `429fc51`
    - `prompt: take types from spec`, промт бере типи зі spec, а не вигадує. SHA: `dac4c0e`
  - Для шляху з ШІ: промт `33f80c3` (абзац «Типи й позначки»); фідбек-коментар: список «Припущення» в `lab-1/ai/chat-trace.md`, де ШІ написав, що типи полів, крім id, вибрав сам; додатковий spec: `429fc51` (`lab-1/spec.md`).
- Розбіжність 2. «Порожнє, поки…» і `optional`
  - Spec (`c4c2bef`): для `returned_at` написано «порожнє, поки книгу не повернули», для `received_at` «порожнє, поки не отримано». Слова «необов'язкове» там немає.
  - Діаграма (`392deee`): обидва поля позначені `"optional"`. Промт велить позначати необов'язкові поля так, але spec для цих двох полів не казав «необов'язкове», тому модель застосувала правило сама, за змістом.
  - Виправлення: один коміт.
    - `spec: mark empty-until fields optional`, у spec записано «необов'язкове, порожнє, поки…» для обох полів. SHA: `609f52a`
    - Промт не змінювався: правило про `"optional"` у ньому вже було, а після правки spec вивід стає однозначним.
  - Для шляху з ШІ: промт `33f80c3` (абзац «Типи й позначки»); фідбек-коментар: список «Припущення» в `lab-1/ai/chat-trace.md` (розділ «Де spec неоднозначний», пункт 1), де ШІ написав, що «порожнє, поки…» позначив як `"optional"`, хоча слова «необов'язкове» в spec немає; додатковий spec: `609f52a` (`lab-1/spec.md`).
- Розбіжність 3. Мінімум примірників у купівлі
  - Spec (`c4c2bef`): у розділі «Зв'язки» написано «Купівля містить багато фізичних примірників». У критерії 13: «Купівля містить лише фізичні примірники». Мінімальної кількості немає.
  - Діаграма (`392deee`): `Purchase |o--|{ Copy`, тобто 1..*. Це вивела модель.
  - Виправлення: один коміт.
    - `spec: purchase has at least one copy`, дописати в критерій 13 «і містить хоча б один примірник». SHA: `24f7a37`
    - Промт не змінювався, бо причина була в неповному spec.
  - Для шляху з ШІ: промт `33f80c3` (розділ «Кардинальності»); фідбек-коментар: список «Припущення» в `lab-1/ai/chat-trace.md` (розділ «Кардинальності, які я вивів із тексту», пункт 3), де ШІ написав, що мінімум 1..* припустив сам, бо spec його не вказує; додатковий spec: `24f7a37` (`lab-1/spec.md`).

**Ключове рішення — які альтернативи зважив і чому обрав цю (ADR):**
Колекція й група як дві сутності, а не одна.

Я розглядала дві сутності й одну сутність із полем типу (наприклад, type). author_id потрібен лише колекціям, owner_id і is_public лише групам, тож частина полів була б порожня залежно від типу, а правила створення й збереження стали б умовними, і діаграма їх не показала б. Тому я обрала дві сутності: ціна цього рішення (дубль title і два зв'язки з Book) менша за проблеми одного варіанта.

Повний ADR з плюсами й мінусами обох варіантів і наслідками для моделі: `lab-1/adr/0001-collection-and-group-as-two-entities.md`

**Перевірка — узгодженість із попередньою моделлю (як перевірив):**
Я порівнювала типи і зв'язки. Я перевіряла все, що ШІ підказувало додати або те, що я просила, також згенероване PNG. ШІ двічі скриптом звірив усі 65 полів і 15 сутностей (назви, порядок, а потім типи) зі spec, а кардинальності та PNG переглянув очима. Назви й порядок сутностей і полів збіглися зі spec дослівно, а кардинальності відповідають розділу «Зв'язки» й критеріям. Я знайшла 3 розбіжності: типи полів, `"optional"` для «порожнє, поки…», мінімум примірників у купівлі. Діаграму за новим промтом не перегенерували, а скриптом перевірили, що типи всіх 65 полів збігаються зі spec. Ліміт 3 броней, «рівно одне з двох» для `library_id` і `purchase_id`, унікальність `Author.user_id` зафіксовані лише у spec.
